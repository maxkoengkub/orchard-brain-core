# Phase 2A: Database Architecture

## Overview
The Orchard Brain Database Layer provides highly scalable time-series persistence using **PostgreSQL** paired with **TimescaleDB**. It seamlessly stores Edge Node telemetry, system events, and the generated multi-agent intelligence results from `OrchardBrain`.

## Technology Stack
- **Database Engine**: PostgreSQL 16
- **Time-Series Engine**: TimescaleDB
- **ORM**: SQLAlchemy 2.0 (Asynchronous)
- **Migrations**: Alembic

## Schema Design

### Time-Series Data (Hypertables)
These tables are converted to TimescaleDB hypertables partitioned by `time`. They use composite primary keys `(time, node_id)`.
1. **`sensor_readings`**: High-frequency telemetry.
2. **`orchard_health`**: Point-in-time results from the `OrchardBrain` intelligence evaluation (`health_score`, `water_stress`, `nutrient_stress`).

### Relational Data (Cascade Delete)
These tables depend on point-in-time evaluations and are linked via `ForeignKeyConstraint` to `(time, node_id)`.
1. **`risks`**: Detected anomalies (e.g., Heat Stress, Drought).
2. **`recommendations`**: Advisory or actionable outputs generated by the RecommendationEngine.

### Stateful & Logging Data
1. **`node_status`**: Stores the latest known state (`battery_pct`, `fw_version`, `uptime_sec`) for each `node_id`. (Relational, Upserted).
2. **`command_history`**: Tracks the state of actuator commands sent to nodes via LoRa. (Time-Series, Standard Postgres).
3. **`system_events`**: Flexible JSON-backed system log.

## TimescaleDB Specifics
In the `database/timescaledb.py` module, raw SQL migrations are provided to:
- Convert tables to Hypertables (`create_hypertable`).
- Configure retention policies to automatically drop raw data after configured intervals (e.g., 2 years).
- Configure compression policies (e.g., chunk compression after 7 days partitioned by `node_id`).

## Connection Management
- Uses **asyncpg** for fully asynchronous operations (critical for the Gateway's asynchronous event loop).
- Maintains a synchronous engine fallback exclusively for Alembic migrations.


# Phase 2A Implementation Walkthrough: Database Layer

I have completely designed and implemented the Database Layer for Phase 2A. 

## What was implemented

### 1. Database Configuration
- **`database/config.py`**: Configured both an asynchronous SQLAlchemy engine (`asyncpg`) for high-performance Gateway insertion and a synchronous engine (`psycopg2`) for Alembic migrations.

### 2. ORM Models
- **`database/models.py`**: Implemented strict ORM schemas representing:
  - `SensorReadingModel`
  - `OrchardHealthModel`
  - `RiskModel` (Composite Foreign Key to `OrchardHealthModel`)
  - `RecommendationModel` (Composite Foreign Key to `OrchardHealthModel`)
  - `NodeStatusModel`
  - `CommandHistoryModel`
  - `SystemEventModel`

### 3. Repository Pattern
- **`database/repository.py`**: Extracted database interactions into an asynchronous `DatabaseRepository` class. It manages transactions, payload conversion (from the Phase 1 `SensorReading` and `OrchestratorResult` models), and upserts (for `NodeStatus`).

### 4. TimescaleDB Setup
- **`database/timescaledb.py`**: Provided a suite of raw SQL commands to convert the telemetry tables into TimescaleDB Hypertables and configure retention/compression policies.

### 5. Alembic Migrations
- Initialized an async Alembic environment. Configured `env.py` to auto-detect model metadata from `database.models.Base`.

### 6. Testing Strategy
- **`database/tests/`**: Configured Pytest to use an in-memory `sqlite+aiosqlite` database fixture. Tests were written to independently verify insertion of readings, evaluations, and node status updates. **All tests pass successfully.**

The implementation seamlessly adheres to the frozen Phase 1 contracts without requiring modification of existing payloads.
